# ADR-002：三应用 Monorepo

- 状态：Accepted
- 日期：2026-07-18
- 关联架构：[三应用职责边界](../architecture/三应用职责边界.md)

## 1. 背景

内部 MOM、供应商门户和客户门户拥有不同用户、数据范围、OAuth Client 和发布节奏，但共享技术栈、设计 Token、API Client 和稳定领域组件。

## 2. 候选方案

### 方案 A：单一应用按角色切换

优点：工程数量少。

缺点：外部门户与内部后台边界模糊，发布、路由、权限和安全配置耦合。

### 方案 B：三个独立仓库

优点：隔离最强。

缺点：共享包、版本、设计系统和 CI 容易漂移，V1 维护成本高。

### 方案 C：一个 pnpm Monorepo，三个可独立部署应用

优点：统一工程治理，同时保留运行和发布隔离。

缺点：需要严格依赖门禁，避免应用互相导入。

## 3. 决策

选择方案 C：

```text
apps/mom-admin
apps/supplier-portal
apps/customer-portal
```

三应用：

- 独立路由。
- 独立构建产物。
- 独立 OAuth Client。
- 独立发布。
- 共享 Workspace 包。

## 4. 共享边界

允许共享：

- API Client。
- Access 契约。
- Design Token。
- 稳定领域组件。
- 通用类型与工具。
- 谱系图能力。

禁止共享：

- 页面。
- 应用 Store。
- 应用私有路由。
- 应用私有业务编排。
- 依赖同版本同时发布的运行时状态。

## 5. 正向后果

- 工程规则和依赖版本统一。
- 共享包可以原子更新。
- 三应用仍保持安全和发布隔离。
- CI 能一次验证整个前端平台。

## 6. 负向后果

- 全仓 CI 可能随应用数量增长变慢。
- 需要防止共享包过度扩张。
- 需要应用级构建和发布脚本。

## 7. 验证

- 应用之间无源码依赖。
- 共享包不依赖应用。
- 三应用可单独构建。
- OAuth 和环境变量可独立配置。
- 单一应用发布不要求其他应用同步发布。

## 8. 替代条件

若某个门户的团队、合规、发布和技术栈长期完全独立，可通过新 ADR 拆仓；拆分前必须提供共享包发布和版本治理方案。

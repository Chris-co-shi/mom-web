# ADR-005：API 模型与 View Model 隔离

- 状态：Accepted
- 日期：2026-07-18
- 关联架构：[Monorepo 与模块边界](../architecture/Monorepo与模块边界.md)

## 1. 背景

后端 DTO 以传输契约为目标，页面模型以用户理解、格式化和组件复用为目标。若组件直接依赖后端 DTO，字段、枚举和可空性变化会贯穿整个 UI。

## 2. 候选方案

### 方案 A：API DTO 直接进入页面和组件

优点：代码少。

缺点：后端契约与 UI 强耦合，门户数据裁剪、格式化和兼容处理散落。

### 方案 B：每个组件自行映射

优点：局部灵活。

缺点：映射重复且难统一，组件承担过多职责。

### 方案 C：在 API 边界统一映射为 View Model

优点：契约变化集中处理，组件输入稳定，便于测试。

缺点：需要维护 Mapper 和额外类型。

## 3. 决策

选择方案 C。

```text
OpenAPI / API DTO
→ Schema Validation
→ Boundary Mapper
→ Page View Model
→ Component Props
```

## 4. 规则

- API DTO 由生成代码或边界类型表示。
- 页面不直接使用数据库 Entity 概念。
- 领域组件只接收 View Model。
- 时间、单位、精度、枚举和可空字段在边界明确处理。
- 外部门户使用裁剪后的 View Model。
- 未知枚举必须有安全回退。

## 5. 正向后果

- 后端字段变化影响集中。
- 组件更稳定、更易测试。
- 三应用可以使用不同展示模型。
- 门户最小披露更容易实施。

## 6. 负向后果

- 类型和映射代码增加。
- 简单页面也需要边界判断。
- Mapper 与契约测试需要维护。

## 7. 验证

- 共享领域组件 Props 不直接引用服务端持久化类型。
- DTO 映射有单元或契约测试。
- 未知枚举不会导致页面崩溃。
- 门户 View Model 不包含内部敏感字段。

## 8. 例外

极简单、稳定、纯技术接口可以暂时使用 DTO，但不得向领域共享组件扩散；进入共享包前必须建立 View Model。

# MOM-Web 渠道与 Portal 边界

> 状态：Approved with Deferred Items  
> 批准日期：2026-08-03 · Chris Review  
> 阶段：MOM Platform P1.6  
> 范围：PC、Mobile、Supplier Portal、Customer Portal 的产品职责，不涉及响应式技术方案

## 1. 推荐渠道模型

保持四个清晰渠道：

|渠道|产品职责|主要用户|
|---|---|---|
|`mom-admin`|内部计划、配置、判断、协同、分析和治理|内部管理员、工厂管理与专业岗位|
|`supplier-portal`|供应商在自身 Party/Factory 范围内参与交货与来料质量协同|Supplier Contact|
|`customer-portal`|客户在自身 Party/Factory 范围内参与履约与质量反馈|Customer Contact|
|`mom-mobile`|现场执行、扫码、采集、快速异常反馈与离线任务|内部 Mobile Worker|

三个 Web 应用保持独立；Mobile 继续作为独立渠道。该结论来自现有 OAuth Client、`user_type`、Party/Factory 隔离和现场离线要求，不是前端技术偏好。

## 2. PC 与 Mobile 边界

### 2.1 PC 负责

- 生产计划、工单下达与跨任务协调。
- 质量判定、放行、异常处置和审批类决策。
- 复杂查询、跨域关联、谱系与影响分析。
- 批量操作、长表单、文档和证据复核。
- IAM/System 平台治理、目录/I18n 发布、审计与受控诊断。
- 对 Mobile、PCS、WCS 回执和业务状态的综合分析。

### 2.2 Mobile 负责

- 现场扫码与对象识别。
- 收货、上架、移库、拣选、投料/生产确认等执行动作。
- 检验结果或现场证据的快速采集。
- 本人任务队列、步骤引导和即时异常反馈。
- 网络不稳定场景下的受控离线命令与恢复。

### 2.3 明确不做

- 不把 `mom-admin` 做成完整移动端替代品。
- 不在 Mobile 承担复杂计划编排、平台治理、批量分析和完整谱系探索。
- 不在 PC 页面直接替代 PLC/DCS/PCS/WCS 的实时设备控制。
- 不以“响应式适配”消除 Mobile 的任务、扫码和离线产品边界。

## 3. PC → Mobile → PC 闭环

产品应支持以下闭环：

```text
PC 创建/下达业务任务
        ↓
Mobile 领取、执行、采集与反馈异常
        ↓
后端记录权威状态与审计
        ↓
PC 查看进度、处理偏差并作出决策
```

闭环成立的产品前提：稳定任务标识、明确状态、责任人、时间戳、幂等执行、冲突反馈和可追溯审计。PC 与 Mobile 不直接相互同步本地状态，均以服务端业务事实为准。

- **Need Backend Confirmation**：Phase 02 任务分配、领取、回执、冲突和离线命令契约。
- **Need Product Decision**：哪些现场任务允许离线，哪些必须在线 fail closed。

## 4. Supplier Portal 边界

### 4.1 每日价值

供应商不只是获得一个外部登录页，而是可以减少邮件/电话往返，清楚知道“需要交什么、工厂是否收到、检验结果怎样、还需补充什么”。

### 4.2 数据范围

- 仅固定 Supplier Party 的数据。
- 仅账号授权 Factory 的协同数据。
- 仅与该供应商直接相关的交货、收货、来料检验结果和受控文档。
- 对越权对象采用防枚举响应，不通过前端隐藏替代后端校验。

### 4.3 操作范围

|能力|阶段|说明|
|---|---|---|
|查看/创建交货协同|Phase 02|以已确认后端用例为准|
|查看到货与检验状态|Phase 02|展示对外可发布状态，不暴露内部草稿|
|补充合规/交付文档|Phase 02 候选|文档类型和病毒/敏感信息策略待确认|
|响应差异或质量问题|Future|需要责任与沟通状态模型|

当前代码中的交货、来料检验、文档能力均为 `planned`，不是 Existing。

### 4.4 禁止访问

- 其他供应商、客户或未授权 Factory 数据。
- 内部用户、角色、权限、会话和安全审计。
- 内部成本、配方、生产工艺、完整库存和设备控制。
- 未对外发布的质量结论、内部讨论和调查材料。
- Application Catalog 管理、Parameter/Dictionary 管理等平台治理能力。

## 5. Customer Portal 边界

### 5.1 每日价值

客户可以在受控范围内掌握履约状态、获取可发布质量信息，并让质量反馈进入可追踪的处理流程，而不是依赖线下询问。

### 5.2 数据范围

- 仅固定 Customer Party 的数据。
- 仅账号授权 Factory 的订单、发运、质量证明和反馈。
- 仅与该客户交付直接相关的追溯结论；不默认暴露完整上游谱系。

### 5.3 操作范围

|能力|阶段|说明|
|---|---|---|
|查看订单/履约状态|Phase 04|MOM 与 ERP 的订单事实边界待确认|
|查看发运与质量证明|Phase 04|仅已发布且允许外发的版本|
|提交质量反馈/投诉|Phase 04|需要附件、状态与响应 SLA 决策|
|查看召回/处置进度|Future|仅展示与本客户相关且允许公开的信息|

当前代码中的订单、发运、质量反馈能力均为 `planned`，不是 Existing。

### 5.4 禁止访问

- 其他客户、供应商或未授权 Factory 数据。
- 内部库存全貌、生产工艺、配方、成本和内部质量调查材料。
- 内部 IAM/System 管理能力。
- 与本客户交付无关的完整批次谱系和召回对象。
- PCS/WCS 控制与内部集成诊断。

## 6. Portal 与 Admin 的关系

- Portal 是外部协同产品，不是 Admin 的换肤版。
- Admin、Supplier、Customer 使用独立客户端和身份边界，不提供 Role Switch。
- 业务状态可以跨渠道协同，但每个渠道只看到其职责所需的视图与动作。
- 内部代办必须在 Admin 内使用受审计委托；不能让内部账号登录 Portal 模拟外部用户。
- 共享的业务事实不意味着共享 DTO、页面或导航；外部 View Model 必须默认最小披露。

## 7. 响应式产品目标

|渠道|目标|
|---|---|
|Admin|桌面优先，完整体验支持 1024px 及以上；不承诺完整手机操作|
|Supplier/Customer Portal|布局支持 360px 及以上的移动浏览器与桌面浏览器；核心查询和轻量协同可用，复杂批量任务仍桌面优先|
|Mobile|以手持设备、扫码和单手现场操作为中心|

- **Product Decision — Confirmed**：Admin 以 1024px 为完整体验下限，Portal 以 360px 为布局下限。
- **Unknown**：供应商/客户真实设备、浏览器、平板、网络与附件上传场景。360px 只定义布局下限，不等于这些真实场景已经通过验证。

## 8. 仍需确认的业务边界

- **Need Backend Confirmation**：MOM 与 ERP 在客户订单、采购交付和结算信息上的权威边界。
- **Need Backend Confirmation**：对外质量状态、质量证明、谱系摘要的发布模型。
- **Need Backend Confirmation**：附件存储、脱敏、病毒扫描和下载审计。
- **Need Product Decision**：Portal 是否需要消息通知；本阶段不假设邮件、短信或站内信已经存在。

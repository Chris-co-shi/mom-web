# ADR-014：用户任务模块与依赖方向

- 状态：Accepted
- 日期：2026-08-02
- 接受日期：2026-08-03
- 决策人：Chris
- 关联架构：[模块边界](../frontend-architecture/05-module-boundaries.md)
- 替代：无

## 1. 背景

MOM-Web 的产品定位是多渠道制造协同工作空间。若按 IAM/System/MES/WMS/QMS 服务或技术目录组织前端，会把平台能力变成超级后台菜单，并让用户任务跨模块泄漏。

## 2. 问题

需要规定模块划分依据、公开入口和依赖方向。此决策不批准 Future 业务模块，也不改变后端领域边界。

## 3. 候选方案

### A. 按后端服务组织

映射简单，但用户任务碎片化且容易生成技术菜单。

### B. 按页面类型组织

List/Form/Dashboard 易统一，但业务语言和数据边界消失。

### C. 按用户任务模块组织

产品语义清楚、可独立演进；需要显式客户端契约连接后端能力。

## 4. 决策

选择 C。依赖固定为 `App Bootstrap / Router / Shell → User-task Modules → Module Public Contracts / MOM Clients → common-ui / design-tokens / pure utilities`。

P1.6 Admin 模块为 People & Access、Security Operations、Experience Governance、Runtime Configuration、Personal Settings。长期域仅作为规划，未经产品和后端契约批准不得创建页面或空目录。

## 5. 决策理由

用户任务是产品导航和变化的主要驱动力；平台能力通过客户端契约支持任务，不占据产品中心。这能避免一个 Admin 加数百技术菜单的超级后台。

## 6. 正向后果

- 页面、路由和语言与角色任务对齐。
- 后端服务演进不必直接重组菜单。
- 模块可以独立测试、懒加载和回滚。

## 7. 负向后果与风险

- 一个任务可能组合多个后端能力，需要明确 View Model 和错误语义。
- 边界评审成本上升。
- 缺少后端聚合时不能靠前端拼成工作台。

## 8. 实施约束

- 应用不互相导入；模块不深层导入；package 不反向依赖应用。
- 禁止共享 Store、循环依赖和前端业务状态机。
- Router 只使用模块公共入口；跨域跳转使用目标模块公开路由契约。
- Portal 与 Admin 保持独立安全、数据和发布边界。

## 9. 验证方式

使用依赖图、深层导入和循环依赖门禁；逐模块检查用户、任务、数据所有者、公开入口、错误状态和禁止依赖。

## 10. 替代或回滚条件

若候选模块缺少用户任务或后端契约，停止创建并标记 `Need Product Decision` / `Need Backend Confirmation`；不得退回按服务自动生成模块。

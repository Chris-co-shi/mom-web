# 权限与数据权限

- 当前阶段：`P1.5：认证与授权闭环`
- 运行时权威：[P1.5 Web 认证与授权运行时基线](P1.5-Web认证授权运行时基线.md)
- 后端协议权威：[mom-platform P1.5 S00 PR #15](https://github.com/Chris-co-shi/mom-platform/pull/15)

## 1. 核心原则

前端权限只用于隐藏、禁用、引导和提示；服务端认证、Permission、Factory Scope、Party Scope、对象归属和领域状态构成最终安全边界。

不得因为前端隐藏按钮、过滤菜单、携带 `X-Factory-Id` 或解析 JWT 就认为操作安全。

## 2. 用户、Client 与应用入口

| 应用 | Client ID | user_type |
|---|---|---|
| MOM Admin | `mom-admin-web` | `INTERNAL` |
| Supplier Portal | `mom-supplier-web` | `SUPPLIER` |
| Customer Portal | `mom-customer-web` | `CUSTOMER` |

三应用采用第一方账号密码 API。登录页由各应用承载，密码只提交 Gateway 下的 IAM 登录接口；当前不建设 BFF。

## 3. `@mom/access` 职责

`@mom/access` 基于 `/api/iam/me` 提供：

- 当前用户与 `user_type`。
- Roles 与 Permissions。
- `factory_ids` 与当前 Factory。
- `party_type`、`party_id` 的只读上下文。
- 应用入口、路由、菜单、按钮和操作体验控制。
- 无权限、应用不匹配和重新认证状态。

不负责：

- 服务端数据权限执行。
- Factory/Party 对象归属。
- 业务状态判断。
- 动态创建 Permission Code。
- 最终授权。

## 4. 权限模型

页面优先使用格式为 `domain:resource:action` 的 Permission Code，不直接依赖角色名。

- Role 可用于工作台推荐和默认导航。
- 同一用户可拥有多个 Role。
- 前端有效权限来自 `/api/iam/me`。
- 不在页面散落 `role === 'ADMIN'`。
- Permission 变化后，在登录、整页刷新或 MOM Admin 首次 403 同步 `/api/iam/me` 后重新构建 Access Context。

前端不实现角色继承、Deny Permission、ABAC 或自定义数据权限 DSL。

## 5. 路由、菜单与按钮

建议路由元数据：

```ts
interface MomRouteMeta {
  title: string;
  permissions?: string[];
  requireAllPermissions?: boolean;
  app?: 'mom-admin' | 'supplier-portal' | 'customer-portal';
  featureFlag?: string;
  factoryContextRequired?: boolean;
}
```

规则：

- 路由、菜单和按钮统一通过 `@mom/access`。
- MOM Admin 使用稳定菜单注册表结合 Permission 生成 Vben 路由；动态菜单中心不是当前依赖。
- 路由元数据不得硬编码服务端数据范围规则。
- 直接调用 API 仍必须由服务端拒绝越权。

## 6. Factory Scope

1. `/api/iam/me` 提供 `factory_ids`。
2. 当前 Factory 可作为普通偏好保存，但启动时必须重新校验。
3. 请求使用 `X-Factory-Id` 传递当前工作上下文。
4. `X-Factory-Id` 不是授权证明，服务端必须验证 JWT Scope 和对象归属。
5. Factory 切换后失效相关查询缓存和页面状态。
6. 前端不支持同一用户在不同 Factory 使用不同 Role。

P1.5 不建设 Warehouse、Workshop、Line、Department 等通用前端 Scope 模型。

## 7. Party Scope

- `SUPPLIER` 用户的 `party_id` 固定为账号绑定的 `supplier_id`。
- `CUSTOMER` 用户的 `party_id` 固定为账号绑定的 `customer_id`。
- Supplier/Customer Portal 不提供主体切换器。
- 前端不得从 URL、下拉框、请求体或本地偏好自由指定 Party。
- 外部 Factory 必须是 Party 有效业务关系与用户授权的交集。
- 内部代办只在 MOM Admin 中展示后端建立的代表上下文，不冒充外部身份。

## 8. 403、404 与空数据

页面必须区分：

- 401：会话需要恢复或重新登录。
- 403：已认证但没有权限，不触发 Token Refresh；MOM Admin 可单飞同步权限，且仅只读请求最多重试一次。
- 404：对象不存在，或服务端为防止枚举隐藏了越权对象。
- 空数据：用户有权限，但当前查询范围没有数据。
- 状态禁止：有权限但领域状态不允许操作。

前端不得根据 404 推断其他 Factory、Supplier 或 Customer 的对象是否存在。

## 9. 门户隔离

Supplier Portal：

- 仅 `SUPPLIER`。
- 固定供应商 Party。
- 不显示其他供应商、内部生产细节或成本。

Customer Portal：

- 仅 `CUSTOMER`。
- 固定客户 Party。
- 不显示内部工艺、供应商、成本或完整生产细节。

`INTERNAL` 用户只能使用 MOM Admin；内部代办必须由后端权限和审计控制。

## 10. 验收

- 三 Client 与三种 user_type 对齐。
- 权限上下文来自 `/api/iam/me`。
- 路由、菜单和按钮无散落角色硬编码。
- 403 不刷新 Token；MOM Admin 权限同步不与 401 Refresh 混用。
- `X-Factory-Id` 不被描述为授权凭证。
- Party 不可由前端自由切换。
- 服务端越权与 404 防枚举有 E2E。

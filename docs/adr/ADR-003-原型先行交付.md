# ADR-003：原型先行交付

- 状态：Accepted
- 日期：2026-07-18
- 关联规范：[Web 原型交付规范](../prototypes/README.md)

## 1. 背景

工业页面包含复杂角色、状态、权限、异步任务、故障恢复和跨领域信息。若直接从接口字段或数据库表开始编码，通常会得到可录入但不可操作、只覆盖成功路径的页面。

## 2. 候选方案

### 方案 A：后端接口完成后直接编码页面

优点：看似启动快。

缺点：用户流程、异常状态和组件边界缺失，返工成本高。

### 方案 B：只写文字需求，不提交原型

优点：文档成本较低。

缺点：布局、信息层级和状态反馈仍然模糊。

### 方案 C：用户流程、状态矩阵、原型、组件和 API 映射先行

优点：设计、业务、架构和实现可以在编码前对齐。

缺点：进入编码前需要额外设计投入。

## 3. 决策

选择方案 C。

页面进入实现前必须交付：

1. 业务目标。
2. 用户角色与数据范围。
3. 用户流程。
4. 页面清单。
5. 页面状态矩阵。
6. Web 原型图。
7. 组件映射。
8. API、权限和错误码映射。
9. 异步、冲突和恢复路径。

原型资产进入：

```text
docs/prototypes/web/<vertical-slice>/
```

## 4. 适用范围

- MOM 管理端。
- 供应商门户。
- 客户门户。
- 页面、Drawer、Modal 和关键领域组件。
- 高影响操作。
- 批次谱系等复杂可视化。

## 5. 正向后果

- 页面从用户任务而不是表结构出发。
- 异常和恢复路径可提前发现。
- 组件和 API 边界更清晰。
- 原型可作为开发和验收依据。

## 6. 负向后果

- 设计阶段时间增加。
- 原型与实现需要持续同步。
- 需要管理图片和设计资产版本。

## 7. 验证

页面 PR 必须能够链接到：

- 需求编号。
- 用户流程。
- 原型。
- 状态矩阵。
- 组件映射。
- API 映射。

缺少任一关键材料时，不进入正式业务实现。

## 8. 例外

纯工程性页面、临时诊断页或极小修复可以简化原型，但必须明确理由；涉及业务命令、权限或复杂状态时不得豁免。

# ADR-001：Vben 5 作为前端参考基线

- 状态：Accepted
- 日期：2026-07-18
- 关联架构：[前端总体架构](../architecture/前端总体架构.md)

## 1. 背景

MOM 管理端需要成熟的后台布局、路由、权限、主题、国际化和工程化能力，但直接复制完整通用后台会引入大量演示业务、既有权限模型和难以治理的历史结构。

## 2. 候选方案

### 方案 A：完全从零搭建

优点：边界最纯净。

缺点：需要重复建设大量成熟后台基础能力，V1 成本高。

### 方案 B：整仓 Fork Vben 并改名

优点：初始页面丰富。

缺点：演示业务、应用结构、权限和历史代码会成为项目债务，来源与升级难治理。

### 方案 C：以 Vben 5 为参考基线，按 Slice 迁移能力

优点：可以复用成熟思想，同时保持 MOM 自有应用和领域边界。

缺点：需要逐项评估和记录来源。

## 3. 决策

选择方案 C。

参考基线：

- Vue Vben Admin `v5.7.0`。
- Node `22.18+` 或 `24`。
- pnpm `11.7.0`。

MOM 自主拥有：

- 应用名称和发布边界。
- 业务路由。
- 权限与数据范围契约。
- API Client。
- 领域组件。
- 设计 Token。
- 用户流程和原型。

## 4. 引入规则

引入 Vben 能力时必须记录：

- 上游仓库和 Tag。
- 原始路径或能力位置。
- 复用方式：依赖、参考重写或源码迁移。
- MOM 修改。
- License 和 NOTICE。
- 后续升级策略。

禁止批量改包名复制完整演示项目。

## 5. 正向后果

- 获得成熟后台架构参考。
- 缩短布局、路由和主题等基础能力建设时间。
- 保持 MOM 三应用和领域设计独立。

## 6. 负向后果

- 引入能力需要额外来源登记。
- Vben 版本升级不能直接覆盖 MOM 代码。
- 需要维护适配和迁移说明。

## 7. 验证

- 仓库中不存在未登记的 Vben 批量源码。
- 所有 Vben 衍生代码可追溯到上游位置。
- 三应用仍可独立构建和发布。
- Vben 权限或演示业务未成为 MOM 业务模型。

## 8. 替代条件

若后续 Vben 架构与 Vue/Vite 技术基线严重不兼容，可通过新 ADR 迁移，但保留 MOM 自有应用、共享包和设计资产边界。

# ADR-008：P1.5 Web 认证运行时

- 状态：Superseded
- 日期：2026-07-19
- 替代决策：[ADR-009：P1.5 Web 第一方认证运行时](ADR-009-P1.5-Web第一方认证运行时.md)
- 关联文档：[P1.5 Web 认证与授权运行时基线](../architecture/P1.5-Web认证授权运行时基线.md)
- 后端权威：[mom-platform P1.5 S00 PR #15](https://github.com/Chris-co-shi/mom-platform/pull/15)

## 1. 背景

三套 Web 应用需要在不建设 BFF 的前提下接入统一 IAM，同时避免浏览器持久化 Token、并发刷新风暴、Client/user_type 混用和前端权限被误当成最终安全边界。

## 2. 候选方案

### 2.1 BFF + 应用 Session Cookie

浏览器不接触 Token，但需要新增 BFF、应用 Session、CSRF、部署和跨应用会话边界，不符合 P1.5 冻结方案。

### 2.2 浏览器持久化 Token

使用 localStorage、IndexedDB 或持久化 Pinia 可以简化刷新恢复，但扩大 XSS 后的长期凭证暴露面，不采用。

### 2.3 Public Client + 顶层 PKCE + 内存 Token

三应用分别作为 Public Client，Token 只在内存，页面刷新重新执行顶层 PKCE；IAM 登录状态提供快速恢复。

## 3. 决策

以下是历史决策，已由 ADR-009 替代。当前三个 PC 应用使用第一方账号密码 API 与当前标签页 `sessionStorage` 会话；`@mom/auth` 仅保留为 OAuth/OIDC/PKCE 兼容能力。

历史方案 2.3：

1. `mom-admin-web`、`mom-supplier-web`、`mom-customer-web` 分别对应三套应用。
2. 使用 Authorization Code + PKCE S256 + OIDC。
3. Access Token 与 Refresh Token 只存在内存。
4. `sessionStorage` 只保存 `state`、`nonce`、`code_verifier`、`returnUrl`。
5. 页面刷新后重新执行顶层 PKCE，不使用 hidden iframe。
6. 不使用 localStorage、IndexedDB、持久化 Pinia、普通 Cookie 或跨标签 Token 同步。
7. 建立 `@mom/auth`、`@mom/access`、`@mom/api-client` 三层职责。
8. 401 使用 Single Flight Refresh，每个业务请求最多重试一次；403 不刷新。
9. `/api/iam/me` 是正式前端权限上下文来源。
10. `X-Factory-Id` 只表示工作上下文，不是授权证明。
11. Supplier/Customer Portal 不提供 Party 切换。
12. 前端路由、菜单和按钮判断只改善体验，服务端执行最终授权。

## 4. 后果

### 正向

- Token 不落入长期浏览器存储。
- 三应用 Client 和用户类型边界明确。
- 并发 401 不会形成刷新风暴。
- Web 与 Mobile 共享同一后端 Token/Session 协议。

### 负向

- 页面刷新需要一次顶层授权跳转。
- Auth Runtime 的状态机、Callback 校验和错误恢复复杂度增加。
- 三应用不共享 Token，跨应用跳转需要目标应用重新授权。

## 5. 验证

- 浏览器存储敏感信息扫描。
- PKCE、state、nonce、Callback 地址清理。
- 三 Client 与 user_type 入口隔离。
- 并发 401 单次 Refresh。
- 403 不刷新。
- 页面刷新和 IAM 登录状态快速恢复。
- `/api/iam/me`、Factory 偏好和 Party 固定测试。

## 6. 替代条件

只有通过新的跨仓库 ADR 才能评估 BFF 或其他会话架构。不得局部回退为浏览器持久化 Token、应用 Cookie API 或前端最终授权。

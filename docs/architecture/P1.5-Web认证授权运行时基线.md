# P1.5：Web 认证与授权运行时基线

- 状态：Current / Accepted
- 当前决策：[ADR-009：Web 第一方认证运行时](../adr/ADR-009-P1.5-Web第一方认证运行时.md)
- 历史决策：[ADR-008：PKCE/内存 Token 方案](../adr/ADR-008-P1.5-Web认证运行时.md)
- 后端协议权威：`mom-platform`

## 1. 当前真实状态

P1.5 已完成三应用、第一方登录、首次改密、当前标签页会话、Single Flight Refresh、`/api/iam/me`、MOM Admin 权限管理、固定 Party Portal 和安全 E2E。

当前三个 PC 应用不直接执行 PKCE。`@mom/auth` 作为标准 OAuth/OIDC/PKCE 兼容能力保留，应用实际使用 `@mom/first-party-auth`。

## 2. Client/user_type

| Web 应用 | Client ID | 允许 user_type |
|---|---|---|
| `apps/mom-admin` | `mom-admin-web` | `INTERNAL` |
| `apps/supplier-portal` | `mom-supplier-web` | `SUPPLIER` |
| `apps/customer-portal` | `mom-customer-web` | `CUSTOMER` |

- Client ID 表示应用，不表示用户。
- 三应用的 Token、Store 和 Refresh Flight 相互隔离。
- Client/user_type 或外部 Party 不匹配时 Fail Closed。
- 内部人员只能进入 MOM Admin；两个外部门户不提供 Party 切换。

## 3. 登录协议

三个应用承载自己的第一方账号密码登录页，IAM 只提供后端 API：

```text
POST /api/iam/auth/login
POST /api/iam/auth/password/change-required
POST /api/iam/auth/refresh
POST /api/iam/auth/logout
GET  /api/iam/me
```

当前不建设 BFF，不使用应用 Session Cookie，也不要求 IAM 独立登录页面。

## 4. 模块职责

### `@mom/first-party-auth`

- 登录、首次改密、Refresh、Logout。
- 当前标签页 `sessionStorage` Token 存储与恢复。
- Token 到期判断和 Single Flight Refresh。
- 登出失败时仍清理本地会话。

### `@mom/auth`

- 保留 OAuth/OIDC、PKCE、Callback 与 JWKS 校验实现。
- 当前三个 PC 应用不直接使用。
- 不得与第一方运行时同时接管同一应用会话。

### `@mom/access`

- 加载并校验 `/api/iam/me`。
- 提供 Permission、Factory、Party 与 Client/user_type 上下文。
- 控制路由、菜单、按钮和页面体验。
- 不执行服务端最终授权。

### `@mom/api-client`

- 只访问 MOM Gateway。
- 注入 Bearer Token、Correlation ID、`X-Factory-Id` 和幂等键。
- 统一 401、403、404、409、429、5xx 与网络错误。
- 不直接保存 Token。

## 5. Token 与偏好存储

- Access/Refresh Token：只由 `@mom/first-party-auth` 写入当前标签页 `sessionStorage`。
- Token 不进入 localStorage、IndexedDB、Cookie、URL、日志、持久化 Pinia 或 Vben Preferences。
- 当前 Factory 与 Vben 主题/布局可作为普通偏好保存，但每次加载权限上下文后必须重新校验。
- 页面刷新可恢复当前标签页会话；关闭标签页后不保留；不跨标签同步。

## 6. `/api/iam/me`

`/api/iam/me` 是前端权限上下文权威来源，提供：

- 用户标识和显示信息
- Client 与 `user_type`
- Roles 与 Permissions
- `factoryIds` 与当前 Factory
- `partyType`、`partyId`

前端不得仅解析 JWT 构造完整权限上下文。

## 7. 401

1. 同一应用同时只发起一个 Refresh。
2. 并发 401 等待相同 Promise。
3. Refresh 成功后，每个业务请求最多重试一次。
4. Refresh 失败、Session 结束或网络结果不可安全恢复时清理会话并进入登录。

## 8. 403

基础原则是 403 不刷新 Token。

MOM Admin 在迁移 Vben 后增加权限变更同步：

- 首次 403 单飞刷新 `/api/iam/me`、Permission 与菜单。
- GET/HEAD 同步成功后自动重试一次。
- 写请求不自动重试，提示用户确认后重新操作。
- 重试仍 403 时进入无权限页，不循环同步。

## 9. Factory 与 Party

- `X-Factory-Id` 只是工作上下文，不是授权证明。
- Factory 偏好必须重新与 `/api/iam/me.factoryIds` 校验。
- Supplier/Customer Party 固定为账号绑定主体。
- 前端不得从 URL、输入框、请求体或本地偏好自由指定 Party。
- 服务端执行 Permission、Factory、Party、对象归属和领域状态的最终授权。

## 10. 路由与菜单

- 页面使用 Permission Code，不依赖角色名授权。
- 当前 MOM Admin 使用稳定菜单注册表与 Permission 生成菜单。
- IAM 尚未提供动态菜单接口，本轮不得虚构。
- 菜单国际化和后端偏好同步均作为明确 Pending 待办。

## 11. 错误边界

- 404：显示“对象不存在或不可访问”，防止枚举。
- 409：不盲重试写命令，刷新最新版本并要求重新确认。
- 429：遵守 `Retry-After`，不放大请求。
- 5xx/网络：查询可显式重试，写命令进入结果确认。
- 错误提示不得暴露 Token、内部地址、SQL、堆栈或对象存在性。

## 12. 验收

- 第一方登录、首次改密、当前标签页恢复、Refresh Single Flight 和登出清理测试通过。
- Client/user_type/Party 入口矩阵 Fail Closed。
- Token 存储静态门禁通过。
- 401/403 重试上限通过。
- 三应用类型检查与生产构建通过。

# P1.5：Web 认证与授权运行时基线

- 状态：**Current / Accepted**
- Slice：`P1.5 S00`
- 后端协议权威：[mom-platform P1.5 S00 PR #15](https://github.com/Chris-co-shi/mom-platform/pull/15)
- 本仓库职责：浏览器运行时实现细节

> 本文不得重新定义用户、Client、Token、Claims、Session、RBAC、Factory/Party Scope、Gateway 或业务服务授权语义；这些内容以 `mom-platform` 权威设计为准。

## 1. 当前真实状态

本基线已完整实施：三应用 Monorepo、OAuth/OIDC、`@mom/auth`、内存 Token 生命周期、Single Flight Refresh、`/api/iam/me`、MOM Admin、固定 Party Portal 与三门户安全 E2E 均已完成并合并。

S00 用于冻结设计；S08～S10 与 S12 已按本基线完成 Vue/TypeScript 实现和验收。

## 2. 三应用与 Client/user_type 矩阵

| Web 应用 | Client ID | 允许 user_type | 禁止 user_type |
|---|---|---|---|
| `apps/mom-admin` | `mom-admin-web` | `INTERNAL` | `SUPPLIER`、`CUSTOMER` |
| `apps/supplier-portal` | `mom-supplier-web` | `SUPPLIER` | `INTERNAL`、`CUSTOMER` |
| `apps/customer-portal` | `mom-customer-web` | `CUSTOMER` | `INTERNAL`、`SUPPLIER` |

规则：

1. Client ID 表示应用，不表示用户。
2. 三套应用均为 Public Client，无 `client_secret`。
3. Redirect URI 必须精确匹配。
4. `INTERNAL` 用户不能进入 Supplier Portal 或 Customer Portal。
5. 内部人员代办外部业务只能在 MOM Admin 中完成，前端不得切换或冒充外部身份。
6. Supplier Portal 与 Customer Portal 不提供主体切换器。

## 3. 登录协议

三套 Web 应用统一使用：

- Authorization Code
- PKCE `S256`
- OpenID Connect
- 顶层页面重定向
- IAM 登录页面输入账号密码

不建设 BFF，不使用应用 Session Cookie 调用 Gateway API。IAM 自己的 HttpOnly Cookie 只维护 IAM 登录页面状态与基础 SSO，不是应用 Token 或 Gateway API 凭证。

## 4. `@mom/auth`

`@mom/auth` 是计划新增的共享包，负责：

- 生成和保存一次性 PKCE 事务。
- 发起顶层 Authorization Request。
- 验证 `state`、`nonce` 和回调参数。
- 使用 Authorization Code + `code_verifier` 交换 Token。
- 内存保存 Access Token、Refresh Token 和最小 Session 元数据。
- Token 到期判断、Single Flight Refresh 和退出。
- 页面刷新后的顶层 PKCE 恢复。
- 服务端 Session 撤销后的重新认证。

`@mom/auth` 不负责：

- 业务 Permission 判断。
- 菜单、路由或按钮过滤。
- Factory/Party 对象归属。
- Gateway 或业务服务最终授权。
- 在持久化存储中保存 Token。

## 5. `@mom/access`

`@mom/access` 负责基于 `/api/iam/me` 提供：

- 当前用户与 `user_type`。
- Role 与 Permission 集合。
- `factory_ids` 与当前 Factory 运行时上下文。
- `party_type`、`party_id` 的只读展示语义。
- 路由、菜单、按钮和操作体验控制。
- `hasPermission`、`hasAnyPermission`、`hasAllPermissions` 等统一判断。
- 无权限、重新认证和应用入口不匹配状态。

`@mom/access` 的判断只改善用户体验，不构成安全边界。服务端仍必须执行 Permission、Factory Scope、Party Scope、对象归属和领域状态校验。

## 6. `@mom/api-client`

`@mom/api-client` 负责：

- 仅访问 MOM Gateway。
- 从 `@mom/auth` 获取内存 Access Token，并注入 Bearer Header。
- 传播/生成 Correlation ID。
- 注入当前 `X-Factory-Id`。
- 统一响应解包、错误转换、超时、取消、幂等键和文件下载。
- 协调 401 的 Single Flight Refresh。
- 处理 403、409、429 和 5xx 的基础语义。

`X-Factory-Id` 只是当前工作上下文，不是授权证明。API Client 不得用前端 Factory 偏好绕过服务端授权。

## 7. Token 存储

### 7.1 只存在内存

- Access Token：只存在内存。
- Refresh Token：只存在内存。
- ID Token：不调用业务 API；只保留运行时确有必要的最小信息。

禁止使用：

- localStorage 保存 Token。
- IndexedDB 保存 Token。
- 持久化 Pinia 保存 Token。
- 普通 Cookie 保存应用 Token。
- hidden iframe silent renew。
- 跨标签页 Token 同步。

### 7.2 `sessionStorage` 允许内容

`sessionStorage` 只允许保存当前一次授权事务：

- `state`
- `nonce`
- `code_verifier`
- `returnUrl`

Callback 完成或失败后必须立即清理。

## 8. Callback 与地址栏清理

1. 验证 `state`。
2. 验证回调错误、Code 和预期 Client/Redirect URI。
3. 使用 `code_verifier` 交换 Token。
4. 验证 OIDC `nonce` 和必要 ID Token 元数据。
5. 清理 `sessionStorage` 中的一次性事务。
6. 使用 `history.replaceState` 或等价方式从地址栏移除 Authorization Code 和临时参数。
7. 调用 `/api/iam/me` 初始化权限上下文。
8. 校验 Client 与 `user_type`，不匹配时安全退出并显示明确错误。
9. 恢复经校验的 `returnUrl`。

## 9. 页面刷新与 Session 恢复

由于 Token 不持久化，页面刷新后：

1. 清空旧内存状态。
2. 发起新的顶层 PKCE Authorization Request。
3. IAM 可利用自己的登录状态快速完成授权，通常无需再次输入密码。
4. 回调后重新获取 Token 和 `/api/iam/me`。
5. 重新校验当前 Factory 偏好。

不使用 hidden iframe 或持久化 Refresh Token 实现 silent renew。

## 10. Single Flight Refresh

1. 同一应用实例同一时间只允许一个 Refresh 请求。
2. 其他遇到 401 的请求等待同一个 Promise/结果。
3. Refresh 成功后，每个原业务请求最多自动重试一次。
4. Refresh 失败、Session 撤销或绝对期限到达时，拒绝等待队列并进入重新登录。
5. 403 不触发 Refresh。
6. 网络不确定时不得形成无限 Refresh 或业务请求重试循环。
7. 三个 Web 应用互不共享 Token 或刷新状态。

## 11. `/api/iam/me`

`/api/iam/me` 是正式前端权限上下文来源，至少提供与后端协议一致的：

- 用户标识与显示信息。
- `user_type`。
- 当前 Client/应用访问结果。
- Roles。
- Permissions。
- `factory_ids`。
- `party_type`、`party_id`。
- Mobile Access 等必要状态（仅相关页面使用）。

前端不得只解析 JWT 后自行构造完整权限上下文，也不得依赖动态菜单中心作为 P1.5 前置条件。

## 12. 当前 Factory

1. 当前 Factory 可作为普通偏好保存，但不得保存 Token 或授权结论。
2. 启动和 `/api/iam/me` 更新后必须重新校验偏好是否仍在 `factory_ids` 中。
3. 无有效偏好且用户有多个 Factory 时，要求显式选择。
4. `X-Factory-Id` 随请求发送，但服务端仍需验证 Scope 和对象归属。
5. Supplier/Customer Portal 只展示主体有效关系中的授权工厂，不允许切换 Party。
6. Factory 切换后失效相关查询缓存和页面状态。

## 13. HTTP 状态处理

### 401

- 仅触发一次 Single Flight Refresh。
- 每个业务请求最多重试一次。
- 恢复失败后重新登录。

### 403

- 不刷新 Token。
- 显示无权限或应用入口不匹配。
- 不把 403 伪装成空数据。

### 409

- 显示版本冲突、状态变化、幂等冲突或结果未知。
- 命令不盲目自动重试。

### 429

- 使用 `Retry-After` 等服务端信息。
- 不立即自动重试形成放大。

### 5xx / 网络错误

- 显示 Correlation ID。
- 查询可按策略重试；命令默认不自动重试。
- 结果未知时进入查询最终状态或人工确认。

## 14. 路由、菜单与按钮

- 页面优先依赖 Permission Code，不直接依赖角色名。
- 路由、菜单和按钮统一经过 `@mom/access`。
- 动态菜单中心不是 P1.5 依赖；菜单可由本地路由定义结合 Permission 过滤。
- 前端隐藏、禁用和引导不能替代后端授权。
- 对其他 Factory、Supplier 或 Customer 的对象，服务端可能返回 404；前端不得据此推断对象是否存在。

## 15. 明确废弃的方案

以下方案在 P1.5 中不是 Current：

- BFF 主方案。
- 应用 Session Cookie 调用 Gateway API。
- localStorage/IndexedDB/持久化 Pinia 保存 Token。
- 前端最终授权。
- 动态菜单中心作为认证授权前置依赖。
- 前端可自由切换 `party_id`。
- `X-Factory-Id` 作为授权凭证。

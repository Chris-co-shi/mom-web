# 状态管理与数据流

## 1. 目标

前端状态必须清晰区分服务端权威状态、页面交互状态、应用会话状态和可持久化偏好，避免把所有数据放入全局 Store。

## 2. 状态分类

### 2.1 服务端状态

示例：

- 工单状态。
- 库存余额。
- 检验结果。
- PCS/WCS 任务状态。
- 批次谱系。

规则：

- 服务端是唯一权威来源。
- 前端缓存不能改变业务真相。
- 命令完成后通过返回结果或重新查询确认。
- 不在 Pinia 中长期保存大量服务端列表作为事实库。

### 2.2 会话状态

示例：

- 当前用户。
- 当前工厂。
- 权限集合。
- OAuth 会话状态。
- 应用版本。

由 Access 层和应用级 Store 管理。

### 2.3 页面状态

示例：

- 筛选条件。
- 当前分页。
- 选中行。
- 对话框开关。
- 表单草稿。
- 当前 Tab。

优先留在页面或页面级组合函数中，只有跨路由恢复有明确需求时才提升作用域。

### 2.4 用户偏好

示例：

- 表格列显示。
- 页面密度。
- 主题。
- 常用筛选。

允许持久化，但必须：

- 有版本。
- 可重置。
- 不包含 Token 和敏感业务数据。

## 3. 单向数据流

```text
Route / User Action
→ Page Controller / Composable
→ API Boundary Mapper
→ API Client
→ Gateway
→ Response / Error
→ View Model
→ Component Rendering
```

领域组件通过 Props 接收 View Model，通过 Event 发出用户意图，不直接访问 API 或全局 Store。

## 4. 命令状态模型

命令操作至少支持：

```text
IDLE
→ VALIDATING
→ SUBMITTING
→ ACCEPTED / SUCCEEDED
→ FAILED / CONFLICT / UNKNOWN
```

`UNKNOWN` 表示请求超时或连接中断，前端不能确定服务端是否已执行。此时应：

1. 停止自动重复提交。
2. 保留 idempotency key。
3. 查询业务对象或命令状态。
4. 向用户说明正在确认最终结果。

## 5. 异步任务状态

统一表达：

- `PENDING`
- `DISPATCHED`
- `RUNNING`
- `BLOCKED`
- `RECOVERING`
- `MANUAL_TAKEOVER`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`

页面应展示：

- 当前状态。
- 最后更新时间。
- 当前步骤。
- 错误摘要。
- 关联命令或事件 ID。
- 可执行恢复动作。

## 6. 列表与详情一致性

- 列表摘要不替代详情权威查询。
- 详情更新后应刷新相关列表摘要或使其失效。
- 多 Tab 或多用户并发导致版本变化时，应提示数据已更新。
- 不通过前端乐观修改伪造已完成状态。

## 7. URL 状态

适合进入 URL：

- 业务对象编号。
- 分页和可分享筛选。
- Tab 或视图类型。
- 追溯方向和根批次。

不适合进入 URL：

- Token。
- 个人敏感信息。
- 大量表单内容。
- 内部数据库主键。

## 8. 持久化策略

| 状态 | 建议 |
|---|---|
| OAuth 会话 | 由统一 Access 策略决定，避免散落存储 |
| 用户偏好 | 可版本化持久化 |
| 表单草稿 | 仅有明确业务需求时持久化 |
| 业务列表与详情 | 默认不长期持久化 |
| 权限集合 | 会话级缓存，可重新获取 |
| 敏感字段 | 不持久化 |

## 9. 验收

- Store 职责可描述。
- 页面刷新行为明确。
- 请求超时不会盲目重试命令。
- 异步状态与后端状态机一致。
- 领域组件不直接访问 API。
